# Hosted debug test benchmark

Run **CI shard benchmark** from the upstream main branch in GitHub Actions. Select **edited** to add a test after restoring a clean seed, or **unchanged** to include the same test in the seed. Run both workloads at the same main revision for a paired comparison. Each dispatch uses twelve standard GitHub-hosted macOS jobs, including one seed build and one artifact producer.

| Layout | Execution |
| --- | --- |
| Cold parallel | Three fresh runners each build and execute one required shard. |
| Serial reuse | One runner builds once, prepares Metal once and executes the three shards in separate test processes. |
| Cached parallel | Three fresh runners restore the same trusted-main debug snapshot, run the normal build and execute their respective shards. |
| Artifact parallel | One fresh runner builds the edited tree with `--prepare-only core`, tars the exact SwiftPM scratch directory and uploads it as a run artifact. Three fresh runners verify the build identity, restore the archive to the same absolute path and execute one shard each with `--reuse-build`, without compiling. |

Layouts run consecutively so they do not compete for macOS slots within the experiment. Production shard filters, explicit case serialization, the MLX library, the core hang sampler and the meetings Python checks are retained. Each shard compares its xUnit method IDs, including explicit skips, to its share of unfiltered SwiftPM discovery. The benchmark also compares results across layouts. Each layout must execute the sentinel method once in core. A failed job, wrong cache identity, incomplete evidence or result mismatch invalidates the comparison.

The artifact producer always builds the edited tree, which is the state a PR would build, so both workloads measure artifact parallel the same way. The tar keeps SwiftPM's symlinks, permissions and absolute workspace paths. Before extracting, each consumer requires the producer's build identity, which covers revision, toolchain, image, workspace and scratch path, manifest, lockfile and harness. It then checks the archive's SHA-256 and size and that its scratch directory is absent. After extracting, it requires a matching tree digest of paths, types, permissions, sizes and link targets. The report repeats these checks across all three consumers. The scratch artifact is named outside the `ci-shard-bench-*` evidence pattern so the report job never downloads it. It is kept for one day.

The job summary and JSON report include wall time from layout eligibility to the last shard finishing, maximum and total queue time, runner-minutes summed across jobs and transfer time. Transfer covers cache restore and archive/upload/download/restore steps. The artifact parallel row starts when the producer becomes eligible and ends when the last shard finishes. It counts the producer's queue, runtime and archive/upload steps, plus each shard's queue from producer completion. Phase rows show the producer and the shards separately. The report also lists the tar size, the uploaded artifact size and the producer's build time. The seed is reported separately because it is a trusted-main cost, while the producer is on the PR path. These durations cover the test layout; release compilation and packaging can still determine the full PR gate time. Runner availability can vary during a dispatch. Repeat measurements before changing the production topology.

The workflow pins the selected main revision and Xcode 26.6. It uses a run-specific cache namespace and deletes the seed after reporting. No paid-runner label or production cache is needed. The temporary debug snapshot uses repository Actions cache capacity while the benchmark is running, and the scratch artifact uses Actions artifact storage until it expires.
